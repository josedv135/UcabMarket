Cómo encaja todo

Arquitectura en tres capas

El navegador solo muestra y pide. El servidor decide (reglas de negocio, sesión, validaciones). La base de datos guarda. Cada capa se puede cambiar sin romper las otras, y eso es lo que luego permite aplicar tácticas arquitectónicas.

Las herramientas, una por una

Qué usamos, por qué es buena y por qué la elegimos

Frontend

Lo que ve el miembro UCAB

HTML · CSS · JavaScript

estructura, estilo, lógica en pantalla
Por qué es buena
  • Es el lenguaje nativo del navegador: no hay que compilar nada.
  • Funciona igual en Chrome, Edge y Firefox.
  • Todo lo demás de este stack se construye encima.

Por qué la elegimos: ya está en la tarjeta Herramientas del equipo y es lo primero que todos saben o pueden aprender rápido.

Descartamos React por ahora: es potente, pero suma una curva de aprendizaje que este proyecto no necesita. Si alguien del equipo ya lo domina, se puede reconsiderar.

Bootstrap

componentes de interfaz listos
Por qué es buena
  • Trae botones, formularios, tarjetas, menús y modales ya diseñados.
  • Rejilla para acomodar el catálogo en columnas sin pelear con CSS.
  • Iconos propios (Bootstrap Icons) y documentación enorme.

Por qué la elegimos: una interfaz consistente y clara sin ser diseñadores. Apoya el rango de calidad Capacidad de interacción.

Descartamos Tailwind: obliga a armar cada componente con clases utilitarias; Bootstrap da el componente terminado.

Backend

Lo que decide el sistema

Node.js + Express

servidor y rutas de la API
Por qué es buena
  • JavaScript también en el servidor: un solo lenguaje para todo el equipo.
  • Express es mínimo: una ruta como POST /api/chats son pocas líneas.
  • Recibe y responde JSON de forma natural.

Por qué la elegimos: aquí viven las reglas de negocio de cada HU (sesión iniciada, máximo 5 fotos, solo el dueño modifica lo suyo). Un backend propio deja ver la arquitectura y aplicar tácticas como el TimeOut del audio de clase.

Descartamos Firebase/Supabase: hacen el backend por ti, y justo eso es lo que la materia pide diseñar.

Socket.IO

chat en tiempo real
Por qué es buena
  • Los mensajes llegan al instante, sin recargar la página.
  • Se monta sobre el mismo servidor Express.
  • Maneja reconexiones solo.

Por qué la elegimos: la meta Chats del Brief es «coordinar la compra por mensajes». Es la pieza de Crear Chat y Añadir Archivos.

Descartamos refrescar cada pocos segundos: más carga al servidor y un chat que se siente lento.

Multer

subida de fotos y archivos
Por qué es buena
  • Recibe archivos en Express con una configuración corta.
  • Limita cantidad, tamaño y tipo de archivo en un solo lugar.

Por qué la elegimos: cubre la restricción del Brief «máximo 5 fotos por publicación» (Añadir Producto) y los archivos del chat (Añadir Archivos).

bcrypt + express-session

seguridad de las cuentas
Por qué es buena
  • bcrypt guarda las claves cifradas: ni el equipo puede leerlas.
  • express-session recuerda quién inició sesión.

Por qué la elegimos: el rango de Seguridad → Integridad (decisión del equipo): la sesión permite que solo cada miembro modifique o elimine lo suyo, y bcrypt guarda la clave encriptada. También permite aceptar solo correos UCAB al crear cuenta.

Datos

Lo que se guarda

Archivos JSON

datos guardados dentro del proyecto
Por qué es buena
  • No hay que instalar ni configurar ningún servidor de base de datos: son archivos de texto en la carpeta db/.
  • JavaScript los lee y los escribe directo (JSON.parse y JSON.stringify); es el mismo formato que viaja entre el navegador y el servidor.
  • Un archivo por conjunto: usuarios, productos, preguntas, chats, mensajes y reseñas.

Por qué la elegimos: el sistema solo se va a correr en una máquina, así que no hace falta un servidor de base de datos. Las relaciones se guardan con ids: un chat guarda el id del producto y los ids de los dos miembros.

Cuidado: todo se lee y se escribe desde un solo módulo del servidor (src/db.js), que guarda el archivo completo en cada cambio. Si más adelante se publica en internet o lo usan muchas personas a la vez, se pasa a una base relacional (SQLite o PostgreSQL).

Trabajo y diseño

Con qué trabaja el equipo

VS Code + Live Server

editor
Por qué es buena
  • Gratis, rápido, con extensiones para todo el stack.
  • Live Server recarga la página al guardar.
  • Thunder Client (extensión) prueba la API sin salir del editor.

Git + GitHub

repositorio del equipo
Por qué es buena
  • Cinco personas en el mismo código sin pisarse.
  • Historial de cada cambio, como el histórico de versiones del Brief.
  • GitHub Desktop si la consola intimida.

Por qué la elegimos: es el «Repositorio Git» que ya está en la tarjeta Herramientas.

Figma

diseño de la interfaz
Por qué es buena
  • Pantallas clicables antes de programar.
  • Los cinco editan el mismo archivo a la vez.
  • Trae kits de componentes de Bootstrap, así lo diseñado coincide con lo programado.

Por qué la elegimos: es el ítem «Diseño de la interfaz (HM)» del Flujo de Trabajo, y la profesora pidió que el producto coincida con el plano: «si hiciste un rancho, tiene que ser un rancho».

draw.io · Canva

diagramas y backlog
Por qué es buena
  • draw.io: diagramas de actividades, casos de uso y arquitectura, con enlace para compartir.
  • Canva: el backlog (story map) que ya tienen.

Ejecución local

correrlo en una máquina
Por qué es buena
  • Basta con node src/server.js y abrir http://localhost:3000 en el navegador.
  • No hay que pagar ni configurar hosting: para la demo basta la laptop de un integrante.
  • Los datos quedan en la carpeta db/ y se pueden revisar a mano.

Cómo el stack cumple los rangos de calidad del Brief

Capacidad de interacción → Operabilidad

Sencilla de usar

«Que la aplicación sea sencilla de usar»

Componentes de Bootstrap reconocibles, diseño probado en Figma antes de programar y mensajes claros en español.

Eficiencia de desempeño → Comportamiento temporal

Catálogo rápido

«Rápida en las funcionalidades del catálogo de productos»

El servidor carga los JSON en memoria al arrancar y el catálogo se pagina: Express responde solo los productos de la página que se ve.

Seguridad → Integridad

Cuentas resguardadas

«Que la información confidencial de las cuentas esté resguardada»

Solo cada miembro modifica o elimina lo suyo (el servidor lo valida con la sesión), las claves se guardan con bcrypt y el chat no muestra correo ni teléfono.

Flexibilidad → Adaptabilidad

Varios navegadores

«Que pueda abrir en varios navegadores web»

HTML, CSS y JavaScript estándar con Bootstrap: funcionan igual en Chrome, Edge y Firefox de escritorio.

Para arrancar

Primeros pasos y estructura del proyecto

Instalar y crear el proyecto

  1. Instalar Node.js (versión LTS), VS Code y Git.
  2. Crear el repositorio en GitHub y clonarlo.
  3. Dentro de la carpeta del proyecto:
    npm init -y
npm install express socket.io multer bcrypt express-session
  4. Cada integrante trabaja su HU en una rama propia y la une con un pull request.
